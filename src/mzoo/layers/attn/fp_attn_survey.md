# FP8 / FP4 attention survey — what to copy for a **training** kernel on SM120/121

Scope: forward **and backward** on GB10 (sm121, 99 KB smem, `mma.sync` only, 273 GB/s).
Target model = DSV4.1 CSA2: SWA KV cached FP8 e4m3 + ue8m0/32ch, main KV cached FP4 e2m1 + e4m3/16ch
(NVFP4 minus the global scale) and dequantized before attention, indexer Q/K MXFP4 used in a real fp4×fp4 matmul.
Quantizers we must be bit-faithful to: `_fake_quant_fp8_block` / `_fake_quant_fp4_block` in `archs/dsv4/modeling_deepseek_v41.py`.

Disagreements worth knowing: (a) SageAttn3 / NVIDIA / FA4-FP4 all rank NVFP4 ≫ MXFP4 for attention, yet DMA measures MXFP4 *faster* than NVFP4 on B200 and DSV4.1 §2.4.4 knowingly picks OCP **MXFP4 for the indexer** "despite the higher accuracy of alternative formats in our experiments", for portability. (b) **"FP4 KV cache" ≠ "FP4 attention"** — FP4 *storage* with FP8/BF16 *math* is near-lossless on RULER (94.6 vs 95.6), uniform FP4 *math* collapses it (0.385 vs 0.859). Every apparent contradiction in this literature is this conflation. (c) Attn-QAT drops SageAttn3's two-level P rescale and reports that SageAttn3's public kernel "exhibits significant numerical errors in causal attention" — independently corroborated by ffpa-attn, which found SA3 masks on the *original* column index instead of its own permuted one ("causal 直接坏 — max_abs 3.3"). ThriftAttention's FP4 baseline is that kernel, so its 0.385 may be pessimistic. (d) Two incompatible MXFP4 *conversion* recipes share the name: OCP §6.3 `X = 2^(⌊log2 amax⌋ − 2)` saturates the block max whenever amax's mantissa > 1.5; NVIDIA's round-`amax/6`-up-to-a-power-of-two wastes a binade. Ours (`_pow2_ceil_scale(amax/6)`) is NVIDIA's, not OCP's.

## 2. (1) Low-precision Q·Kᵀ

Everyone quantizes Q/K and nobody found a reason not to; the disagreements are only about granularity and smoothing.
Convergent evidence: **per-block (never per-tensor)** — FA3's own ablation is 2.4e-2 → 9.3e-3 from that change alone, and the extra Hadamard buys only 9.3e-3 → 9.1e-3, i.e. **incoherent processing is not worth it once the blocks are small**. Below ~16-channel blocks (NVFP4/MXFP4) the mean-subtraction trick matters again: ffpa-attn makes smooth-Q *and* smooth-K mandatory on fp4 and pays for a rank-1 `Δs` correction kernel.

**Recommendation.** Keep the main `S = Q·Kᵀ` in **BF16** for now. Reasons, in order:
(a) DSV4.1 keeps Q in BF16 by construction, so a low-precision QK would be *our* approximation, not the model's — it changes the trained function and needs its own QAT;
(b) the long-context evidence is against it: ThriftAttention's RULER sweep is the only one that exists and uniform NVFP4 Q/K/P/V costs Llama3.1-8B **0.859 → 0.385**, needing 5 % FP16 block-pairs to claw back to 0.770; DMA has to keep a 128-token diagonal window *and* a 128-token sink window in MXFP8 and V in FP16 to gain 2 LongBench points. Our CSA2 rows already have a learnable sink and a 128-token window — exactly the structures those papers protect in high precision;
(c) on GB10 the fp8/fp4 mma is not the bottleneck — measured fp4 ≈ fp8 block-scaled throughput (ffpa) and 1.2–1.5× not 2× at the GEMM level (NVIDIA forum), against 273 GB/s of DRAM;
(d) FA3's FP8 path has **no backward**, and neither does any public sm120 fp4/fp8 attention, so there is no reference design to copy for dQ/dK.
If we later want it: per-block scales on the (Bᵣ×d, B_c×d) tiles, K mean-subtracted (correct the LSE by `+scale·⟨q_row, k̄⟩`), no Hadamard.

## 3. (2) Low-precision P·V

P ∈ [0,1] is *not* a dynamic-range problem for a float format — it is a **scale-encoding** problem, and each family solves it differently:
- SageAttn2 and ffpa-attn: **static `δ_P = 1/448`**. Free (one global dequant constant, so the PV mma accumulates straight into `o_acc`), and exact-ish because `rowmax(P̃) = 1` under online softmax.
- SageAttn3 / ffpa-fp4: the e4m3 *block scale* of NVFP4 would sit in [0, 1/6], so they add a first level `s_P1 = rowmax(P̃)/(448·6) = 1/2688` and fold it into the `exp2` argument; 93.32 → 99.52 % cos-sim.
- FA4-FP4 "Direct-P": map log-softmax scores to e2m1 codes with an affine classifier `max(0, Ax+B)`, skipping the exponential.
- cuDNN MXFP8 attention and FA3: a **fixed scale of 256 = 2⁸** (`flash::Softmax<..., Max_offset = !Is_FP8 ? 0 : 8>`), justified identically — "softmax output is bounded [0,1]". Two independent implementations, two different constants (256 vs 448); both work because all that matters is landing the row in the format's sweet spot.
- Attn-QAT: no rescale at all, QAT absorbs it.

For **training**, the evidence is much sharper and points one way: FA4-FP4 reports that *every* MXFP4 P/V run diverged (loss 7.01 → 16.25 in 25 updates) and selects **FP8 P/V** for training; SageBwd keeps `dP = dO·Vᵀ` in FP16 while INT8-ing everything else; Attn-QAT's backward GEMMs are BF16.

**Recommendation.** `O += P·V` in **BF16** in v1. If we later chase the PV gemm, go **FP8 e4m3 with the static `1/448` P scale and per-channel V**, never FP4, and keep `dP = dO·Vᵀ` in BF16 whatever else changes. Two cheap tricks worth stealing even in BF16: fold the P scale into the `exp2` argument (`exp2(fma(s, L, c))` — no separate normalize pass), and ffpa's tensor-core row-sum (`mma` against an all-ones operand) so `l_i` is exact w.r.t. the *quantized* P.

## 4. (3) Low-precision KV cache dequantized on load

This is the one point where our answer is fixed by the model, not chosen: DSV4.1 §2.4.4 explicitly says **"Dequantizing cached values before attention allows us to use a more accurate format without requiring native matrix-multiplication support"**, and it justifies dropping NVFP4's global scale by a magnitude bound (‖KV latent‖₂ ≲ √512 ≈ 22.6, observed max ≈ 10, vs 448×6 = 2688 headroom).

What matters for a *training* kernel is that the forward must **round-trip through the exact QAT grid**, gradients flow by STE. Bit-faithfulness details that library quantizers get wrong:
- window FP8: `scale = 2^ceil(log2(amax/448))` over 32 channels, `amax` clamped to 1e-4. The **ceil** rule never clips. The OCP MX reference rule is `2^(floor(log2 amax) − emax_elem)`, which *does* clip (amax = 7 → scale 1 → clamp to 6). A stock MXFP8/MXFP4 encoder will not bit-match us.
- main FP4: `scale = e4m3(amax/6)` over 16 channels, `amax` clamped to `6·2⁻⁹`; e2m1 grid `{0,±.5,±1,±1.5,±2,±3,±4,±6}` with RTNE, ties-to-even at 0.25/1.25/2.5/5.0.

Production agrees, unanimously. FlashInfer's FA2 path repacks an fp8/fp4 KV tile into a 16-bit smem staging buffer (`repack_kv_tile_to_16b`) and then does bf16 `ldmatrix` + MMA; NVIDIA's TensorRT-LLM NVFP4 KV cache "requires that values be dequantized from NVFP4 to FP8 before attention"; and **FlashMLA already ships the DSV4.1 FP4 format** — `csrc/kernels/kv_cache_format.h` documents "512 e2m1 packed 2/byte ‖ 32 bytes of float8_e4m3 scales, each covering 16 consecutive e2m1 values", `tests/quant.py` says "the scale is amax / 6 … rounded to e4m3, **without a per-tensor scale**" (288 B/token, valid only as `extra_k_cache` beside the fp8 cache), and `sm100/dequant_utils.cuh::KVBlockDequantizer` does `fp4x8_to_bf16x2x4` + `e4m3x2_to_bf16x2` then `__hmul2`, commenting "**Exact: e2m1 × e4m3 has at most 2 + 4 significant bits**". Their Hopper deep-dive is explicit: "we first dequantize the 512 float8_e4m3 values into 512 bfloat16s … then perform the MQA calculation using MMA operations in bfloat16 precision." Generation-over-generation the quant tile shrinks 128 → 64 → 32 → 16 and the RoPE dims go from bf16-protected (V3.2, V4) to quantized (V4.1). DeepSeek's V4.1-Flash reference `inference/kernel.py` ships our quantizer as a QDQ round-trip — `fp4_quant_kernel(..., block_size, scale_dtype=FE8M0|E4M3, inplace=True)` — with "`# Training's compressed KV: keep even an all-zero group's scale nonzero`" and "`# Compressed KV uses groups of 16 with E4M3 scales; the indexer uses 32 with E8M0`".

**The one performance warning**: FlashMLA reports the fp8 MLA kernel is **dequantization-bound**, 50 CUDA-core cycles/token against 34 MMA cycles, and fixes it with 2-CTA clusters that each dequantize half the KV and `st.async` it into the sibling's smem via DSM (250 → 410 TFLOPS on H800). **sm120 has no DSM and no cluster launch**, so that escape hatch is closed for us — budget the dequant on the critical path.

**Recommendation.** Load FP8/FP4 + scales from gmem, **dequantize into the BF16 smem tile** (design step 3v2/4v2), and keep the GEMMs BF16. On a 273 GB/s part this is a pure bandwidth win (4× on the main cache) that costs nothing in math. Backward: recompute the *same* dequantized tile — do **not** stash a BF16 copy, and do not re-derive scales in the backward. Gradient w.r.t. the cache is the identity (STE) with the scale stop-gradiented, matching `_fake_quant_*`'s out-of-place semantics. Attn-QAT's two fixes are the ones to import verbatim: **(i)** re-apply the P fake-quant in the backward recompute (line 11 of its Alg. 3) or the FA identity `PᵀdP = dOᵀO` breaks and gradients explode; **(ii)** accumulate a second output `O' = Σ_j P̃_ij V^F_j` (high-precision P, quantized V) in the forward and use `D = rowsum(dO ⊙ O')` in the backward. Note their `dS = P ⊙ (dP − D)` uses **unquantized** P while `dV = (P^F)ᵀ dO` uses the quantized one — that asymmetry *is* the STE. Their shipped Triton kernel adds two details the paper omits: the softmax denominator `l_ij = rowsum(high_prec_P)`, not of `P^F`; and `JOIN_QAT_PV`, which concatenates `[P^F ; P]` along M into one `2·B_M × B_N` dot against the shared V so O and O' cost one GEMM, not two (their sm120 default; storage cost ~25 %).

## 5. (4) The DSV4.1 indexer's fp4 × fp4 scoring

This is the only place where FP4 *math* (not storage) is part of the trained model: DeepSeek-V4 states the indexer QK path is "cached, loaded and multiplied entirely in FP4", scores cast FP32→BF16, 2× faster top-k at 99.7 % KV recall. DeepSeek's own public kernel already does it: DeepGEMM `csrc/apis/attention.hpp::fp8_fp4_mqa_logits` takes `q_sf [seq, heads]` / `kv_sf [seq_kv]` as int32 words of 4 packed ue8m0 and its test calls `per_token_cast_to_fp4(..., use_ue8m0=True, gran_k=32, use_packed_ue8m0=True)` — **block-32 ue8m0, i.e. MXFP4, not NVFP4**.

The hardware has it. PTX ISA 9.4 §9.7.16.3 Table 45 lists, for warp-level `mma.sync` on **sm_120a** (and sm_120f from PTX 8.8): `.kind::mxf4` + `.scale_vec::2X` + `.ue8m0` (⇒ block 32 at `m16n8k64`), `.kind::mxf4nvf4` + `4X` + `.ue4m3` (⇒ block 16), and since PTX 9.1 also `mxf4nvf4` + `4X` + `.ue8m0`. Note the mirror-image fact: **`mma.sync` block-scaling does not exist on sm_100a at all** — datacenter Blackwell must use `tcgen05.mma`, which is why SageAttention3 and ffpa-attn are sm120-shaped and FA4-FP4 is not portable to us.

**TileLang, however, exposes only one of them.** `T.mma_gemm_blockscaled` (`tilelang/language/gemm_op.py`) and `src/tl_templates/cuda/instruction/mma_block_scale.h` `static_assert` that the *only* supported instruction is `m16n8k64.kind::mxf4nvf4.block_scale.scale_vec::4X` with **ue4m3** SFs at granularity 16; `sf_layout="cutlass_128x4"` is rejected, only `"blockscaled_chunk_kmajor"` exists, and the sole in-repo call sites are the GEMM example we already vendored plus its unit test. No TileLang example combines a block-scaled MMA with attention at all.

**Recommendation.** Indexer forward: either teach TileLang the `kind::mxf4 / 2X / ue8m0` variant (small, mechanical — one atom in `mma_block_scale.h` plus a `static_assert` widening), or, to avoid touching upstream, **use the block-16 ue4m3 path and re-encode our ue8m0/32 scales into it** — each 32-channel block becomes two 16-channel blocks carrying the *same* power-of-two value, so the re-encode is **exact whenever that power of two lands in e4m3's range (2⁻⁹ … 2⁸)**; pull a per-tensor power-of-two global factor into `softmax_scale` if it does not. The e2m1 codes themselves are untouched, so the score matmul stays bit-identical to `_fake_quant_fp4_block(..., 32)`. That keeps the one GEMM where FP4 is both faithful and free. Indexer backward: **BF16 over the dequantized q/k, straight-through** — same as Attn-QAT, and as `lemyx/tilelang-dsa`, the only public TileLang lightning-indexer *training* operator, which is bf16 with fp8 listed as future work. Two repo-specific caveats: our `_pow2_ceil_scale` is the ceil rule (§4), and `_fake_quant_fp4_block` **detaches the graph** — `archs/dsv4/README.md` already flags that as why the indexer never trains. The STE belongs there, not in the kernel; the kernel only has to agree numerically.

## 7. Open questions

1. Does the ue8m0→ue4m3 re-encode of §5 ever leave e4m3 range on real indexer q/k (scale < 2⁻⁹ or > 2⁸)? One histogram over a training batch settles it; if it does, we need the per-tensor global factor.
2. Arch flag: ffpa reports `sm_120f` (family) is required for `setmaxnreg`; DGX Spark reports vary between `sm_121a` and `sm_121f` for block-scaled mma; SageAttention3's own `setup.py` compiles `sm_121a` for cc 12.1. Our `sm120_nvfp4_blockscaled_gemm.py` hacks `-DCUTLASS_ARCH_MMA_SM120A_ENABLED=1`; settle before step 6.
3. Long-context accuracy for FP4 *attention compute* is reported by exactly one paper (ThriftAttention, RULER) and it is bad; SageAttn3, Attn-QAT, FA4-FP4, ScaleSearch and Full-Stack FP4 all report only cos-sim / VBench / short-context LM benchmarks. For FP4 *KV storage* only TRT-LLM (RULER 64K) and arXiv 2609.04263 (RULER/NIAH, and it shows 2-bit ppl recovery 576→11.4 restores only 11–12 of 180 retrieval cases) have numbers. **We need our own RULER-style check of the FP8/FP4 cache round-trip — perplexity will not detect the failure.**
3b. Does the dequant land on the critical path for us? FlashMLA is dequant-bound at 50 vs 34 cycles/token and escapes via 2-CTA DSM, which sm120 lacks. Measure the fp4→bf16 unpack cost in the step-4 kernel before assuming the 4× bandwidth win is free.
4. The `Δs = q̄(K − k̄)ᵀ` rank-1 correction ffpa needs for fp4 QK is a whole extra kernel. If we ever quantize QK we should first check whether DSV4.1's `kv_norm` + RoPE already centres the latent enough to skip it.
5. Head dim 96 is not a multiple of 64; ffpa pads fp4 tiles to `(D+63)&~63` with zero data *and* zero scale factors. Confirm TileLang's block-scaled path tolerates a zero SF word. Also spike the two bugs its own example documents: `T.copy` of an SFA slice mis-lowers on the bulk-TMA path, and simultaneous M *and* N tail tiles are unsupported.
6. Is `P̄ = 1.0` (arXiv 2510.04212) reachable here? With a per-head learnable sink in the denominator the row max can still produce an exact-1 probability; worth one assertion in the reference.
7. SageAttention3's sm_121a build is the obvious numerical reference to diff against (it is the only artifact that compiles for GB10 today) — but two independent sources say its **causal** path is wrong (Attn-QAT excludes it for "significant numerical errors in causal attention"; ffpa-attn traced it to masking on the unpermuted column index). Validate against its *non-causal* path only, or against FlashMLA's dequantizer.
